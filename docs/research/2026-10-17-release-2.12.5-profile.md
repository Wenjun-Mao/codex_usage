# Release 2.12.5 Wall Time Profile

Date: 2026-10-17 (America/Toronto).

The interval from "Let's do a small release" to the final completion message was
about 39.5 minutes. Only 11 seconds were Marketplace upload commands. The largest
controllable costs were a failed qualification and harness correction, the
two-slot visual matrix, and manual orchestration/receipt preparation. The actual
successful qualification took 12m19s, versus 11m30s recorded for 2.12.4.

This is a retrospective wall-time profile of that release, not a CPU profile or
a new benchmark run. Inputs are timestamped commands in the release turn,
GitHub run/job/step records, local test evidence and the public verification
receipt. It does not rerun qualification, upload anything, or access the usage
ledger. Recommendations below are not workflow changes or new release authority.

### Visual Scheduling Opportunity

All five jobs run on separate macOS runners. Using the observed whole-job
durations and current matrix order, a simple list-scheduling replay gives:

| Visual Slots | Modeled Pool Time |
| --- | ---: |
| Two | 8m36s |
| Three | 6m06s |
| Five | 6m06s |

The actual two-slot pool, from first visual start to last finish, took 8m44s;
small dispatch gaps account for the difference from the 8m36s model. Three slots
could remove approximately 2m30s to 2m40s from this run, reducing qualification to
about 9m40s. This assumes unchanged job durations and available runners; it is a
scheduling estimate, not a measured faster CI run. Reordering within two slots
alone cannot recover that saving because the combined visual workload fills both.

Browser installation cost 24-29s per visual job, roughly 26s on the critical
breakdown job. A correct version/OS-keyed browser cache may help but cannot save
the sum of all five setup times from wall latency. The remaining 5m10s breakdown
work still spans 720 fresh navigations, snapshots and real keyboard interactions.
Further browser sharding or proven navigation-state reuse needs separate timing
and complete tuple/assertion parity, not omitted cases or weakened input checks.

Speeding up Python tests or PyInstaller would not shorten this successful run:
core finished 4m25s before the last visual job, and both packages finished earlier.
Native proof and hosted freeze remain deliberate serial trust boundaries.

## Promotion And Public Verification

Sources: [dry-run](https://github.com/Wenjun-Mao/codex_usage/actions/runs/39086272583),
[promotion](https://github.com/Wenjun-Mao/codex_usage/actions/runs/39086334811),
and the [published receipt](../release/2026-10-17-2.12.5-published.md).

| Promotion Step | Observed Time |
| --- | ---: |
| First proof validation in validation job | 33s |
| Fresh proof/byte validation in publisher job | 33s |
| Complete prior publication history check | 8s |
| Record macOS before-upload intent | 22s |
| Upload macOS | 8s |
| Record Windows before-upload intent | 23s |
| Upload Windows | 3s |

The other roughly 38 seconds are setup, transitions, artifacts and bookkeeping.
The separate credential-boundary revalidation is intentional. Current journal
reads walk pinned Git history through serial API calls, with immutable-object
caching only inside each process; repeated prepare/stamp processes repeat work.
Persistent digest-verified immutable-object reuse could reduce transport without
caching mutable heads or weakening append/readback safety. The 45s journal total
is the maximum observed region to investigate, not an established recoverable saving.

Inspection and tag handoff took 2m24s, despite the dry-run taking only 29s.
Detecting normal qualification completion cost about 28s; local inspection began
about 67s after actual completion. Some remaining time was evidence review,
comparison, tagging and dispatch. A single resumable, bounded coordinator could
perform those routine transitions promptly while preserving explicit approval
and stopping for new failures or ambiguous upload outcomes.

The turn issued 192 shell commands; 33 status/API/artifact reads took a combined
25.8s, mostly overlapping longer waits. Their count is not the principal release
bottleneck, but duplicate watching/status reads add noise and coordination work.
The final 3m02s included a 73.4s context-compaction pause. Receipt checks themselves
took 0.16s. Generating the receipt from verified fields and preparing its narrative
before propagation completes would shorten this closeout substantially.

## Recommended Order

1. Run affected visual contracts before dispatch, so readable-text changes cannot
   reach hosted CI with stale assertions. Preserve the unresolved timing evidence.
2. Trial three isolated visual slots, retaining the full case inventory, runner
   platform and all timing/functional requirements. Measure runner cost and latency.
3. Automate routine wait/inspect/dry-run/tag/promote/verify/receipt transitions under
   the owner's already-required release authority, with bounded waits and resumable
   state. Never upload again merely because catalog entries are not visible.
4. Profile breakdown per browser/operation before sharding it or reducing redundant
   navigation; first prove state-reset and complete assertion equivalence.
5. Optimize proof/journal transport only after measuring request counts; retain
   independent credential-boundary checks, fresh mutable refs and anchored intents.

With the same process and Marketplace wait, a clean release without this failed
cycle would still take about 30 minutes. Three visual slots plus quicker handoffs
and receipt generation suggest roughly 22-25 minutes as an initial public-release
target, not a verified result. Marketplace propagation remains variable. A reliable
sub-20-minute total would need further measured browser-matrix work or a shorter
external validation interval; a faster Python runtime is not the first lever here.

No source code, workflow, timing limit, published package, tag, installed extension
or live data was changed by this profiling task. The earlier
[test/release profile](2026-10-13-verification-and-release-profile.md) preserves the
pre-promotion baseline; the latest process no longer rebuilds on a successful tag.
