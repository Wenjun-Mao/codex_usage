# Codex Usage 2.11.0: Observed Model Speed

## Status And Outcome

Approved for implementation on 2026-10-08. The version is proposed, not bumped.
Implementation, scoped commit/push, and release are authorized. Review and
both nonpublishing platform gates must pass before tagging/publication.

Add useful model-level output-speed summaries and daily/hourly trends from
captured local evidence. Let users compare Astra, Sol, Luna, and other models
over time without splitting the normal view by reasoning effort. Include the
explicit All Projects option and the already-prepared Usage reload-icon removal.

Success means the first installed experience can populate recent charts promptly,
recover all measurable available history gradually, and stay responsive without
changing language accounting or increasing capture frequency.

## Settled Scope

- User approved all available historical logs, recovered in bounded batches;
  prioritize recent activity while ensuring older sources make progress.
- Include model summaries, daily trends, and hourly trends in this release.
- Pool reasoning efforts in the visible model series. Preserve available effort
  metadata for internal checks; do not claim effort can never influence results.
- Provide a genuine unfiltered All Projects option, not just a fixed selection
  of every project currently listed.
- Remove the Usage reload icon; keep Capture Usage, automatic post-capture
  refresh, Storage reload, and the Command Palette recovery command.
- Hourly navigation for long ranges uses navigable seven-local-day windows,
  explicitly selected by the user on 2026-10-08.

The metric thresholds, presentation details, and architecture below form the
approved implementation starting point; they are not already shipped behavior.

## Evidence And Existing Constraints

- Current release is 2.10.5. The existing ledger stores language usage but not
  response-level generation timing suitable for these charts.
- The read-only local probe found usable timing/count pairs and demonstrated
  daily comparisons. It also found collapsed timing, ambiguous pairing, missing
  logs, short-response sensitivity, and uneven model samples. Its private
  artifacts under `output/research/model-speed/` are exploratory evidence, not
  public fixtures or a validated server-performance benchmark.
- The user's supplied announcement names faster subscription generation for
  Astra and Sol. Local observations can show a change, but cannot independently
  establish its cause, universal magnitude, exact rollout time, or service tier.
- Capture already has guarded append checkpoints, one heavy-I/O lane, and
  resumable image backfill. Reports read the ledger, not Codex JSONLs.
- VS Code uses `enableScripts: false`, restrictive CSP, semantic HTML/CSS, and
  allowlisted command URIs. Preserve that security boundary for chart controls.
- Ledger schema is 5; parser cache schema is 10 and parser version is 8.
  Ownership normalization can rebuild event IDs. New timing identity cannot
  depend on those transient IDs or require discarding the existing usage cache.

## Proposed Product Behavior

### Model Summary And Trends

- Add an **Output tok/s** summary to Model Details, calculated over the complete
  selected range and project filter. Keep token/category disclosures intact.
- Place an unframed **Observed Output Speed** chart near Model Mix/Model Details,
  outside Plan Allowance. Reuse model colors and exact model IDs, including new
  models when their evidence is valid; do not merge different model versions.
- Offer Daily/Hourly segmented controls. Default to Hourly for Today/Yesterday
  and Daily for longer ranges. Daily shows the selected calendar range; sparse
  axis labels may reduce clutter but must not silently replace daily values with
  averages of daily medians.
- Hourly detail uses seven-local-day windows. Its visible calendar
  window must be explicit; navigation never changes global date/project filters
  or the all-range model summary. Clamp it to the selected range.
- Show each bucket's median response speed. Tooltips/focused detail expose its
  middle 50% range, eligible-response count, and distinct-task/source count.
  The middle 50% range describes variation, not a confidence interval.
- Display tok/s to one decimal. Empty or insufficient evidence is not zero.
  Leave gaps rather than interpolating through missing buckets.
- Proposed display gates: fewer than five eligible responses produces no numeric
  point; five through nineteen produces a visibly marked small-sample point;
  twenty or more uses the normal point treatment. These are usability gates,
  not statistical confidence claims. Do not require multiple tasks merely to
  show a valid single-task sample; disclose the count instead.
- Use report-local calendar days/hours and preserve distinct offsets during
  repeated DST hours. A local day can contain 23 or 25 hours.
- Keep coverage, exclusions, and backfill progress compact and folded. The chart
  remains usable during partial recovery. Avoid adding standing Plan Allowance
  text or presenting absence of timing as absence of usage.
- Keep filter, granularity, and hourly-window state stable when captures refresh
  the visible report. Provide keyboard-accessible controls and point detail.

### Explicit All Projects

- Give the native project-selection flow an unmistakable **All Projects** action
  alongside choosing a subset. Choosing it stores the existing empty-key filter
  representation and includes subsequently discovered projects automatically.
- Selecting all currently visible checkboxes remains an explicit fixed subset;
  do not silently reinterpret a saved user selection as unfiltered.
- Existing empty selection still means All Projects. Cancel leaves state alone.
  Use canonical project keys despite duplicate display labels.
- Prefer a small native choice followed by the existing multi-select, or an
  accessible picker action. Do not introduce a selectable sentinel that can
  conflict with project checkboxes. The exact native control is an implementer
  choice, subject to these observable rules.

## Proposed Timing Evidence Contract

The metric is **observed output-phase tokens per second**, not pure server decode
speed, first-token latency, or end-to-end task throughput.

1. One observation represents one model response. Match its per-response
   `token_usage_record` to the following trusted language delta, reconciling all
   six token fields, model, turn, source generation, and timestamp ordering.
   Timing items do not supply a universal explicit response foreign key; ordered
   within-turn association must therefore have tested, conservative boundaries.
2. Numerator is trusted `output_tokens`, which already includes reasoning.
   Do not add reasoning twice or use input, cached input, or total tokens.
3. Denominator is the client-observed output-phase envelope: first valid model
   generation item start through the last generated item/output payload end.
   Exclude initial waiting/prefill and reject observed tool execution overlapping
   the envelope. Do not divide by capture intervals or whole task durations.
4. Reject incomplete/ambiguous response boundaries, conflicting duplicate IDs,
   mismatched counts, missing reasoning timing when reasoning was counted,
   negative/collapsed/sub-resolution item timings, mixed turns/models, and
   impossible time ordering. Preserve bounded content-free rejection reasons.
   Do not repair suspicious timing by clipping rates or statistical outliers.
5. Start with the probe's conservative 10 ms minimum item duration and at least
   500 output tokens per displayed response. Validate sensitivity at 50/100 ms
   and 100/2,000 output tokens before accepting these defaults. They reduce known
   timing/short-response problems; they are not universal accuracy guarantees.
6. Retain compact counts, timing bounds, lineage, available context, and metric
   version. Never retain prompts, answers, tool payloads, or reasoning text.
   Unknown client/service-tier metadata stays unknown; do not assume Fast or
   Standard or add default effort splits.
7. Deduplicate replayed/forked/moved response history conservatively. Inherited
   responses must not become extra speed samples. Conflicting observations are
   excluded with a reason, not averaged or resolved by arbitrary arrival order.
8. Assign a whole response to the trusted usage timestamp's half-open range and
   local calendar bucket. Recompute daily/all-range medians from eligible
   response facts, never by averaging hourly or project medians.

Before feature implementation, replay this contract with synthetic adversarial
fixtures and a disposable copy of captured evidence. If pairing cannot be made
defensible for a format, mark it unmeasurable; do not weaken the matching rules
to manufacture coverage. Material changes to the metric return for review.

## Data Flow And Historical Recovery

### Additive, Versioned Facts

- Introduce cohesive timing-domain modules with minimal parser/report wiring.
  Persist bounded in-flight response state across append chunks and restarts;
  older parser checkpoints without timing fields remain readable.
- Add timing cache/ledger tables through explicit additive migrations. Preserve
  existing language events, parser checkpoints, quota/image evidence, settings,
  and source provenance. Do not trigger a global parser-cache drop/reparse.
- Bind timing facts to verified source generation, source-record ordinal, and
  response identity/version, not transient normalized `event_id`. Integrate
  append, replacement, archive/rekey, supersession, and ownership-rebuild paths.
  Reconcile timing facts against their current trusted language event.
- Reuse verified project transitions and final event attribution for filters;
  a naive raw-project SQL filter must not bypass the established contract.
- Track a separate speed-data revision and recovery state. Speed-only recovery
  invalidates speed/report caches, not monetary aggregates or allowance fits.
  Include timing revision in the extension's auto-refresh fingerprint.
- Version the algorithm and derived aggregates. Retain sufficient compact
  primitive evidence to invalidate/recompute changed metrics safely.

### Bounded Backfill

- Recover all still-available active and archived logs, recent first with fair
  progress for older sources. All available history is an inventory policy, not
  a guarantee that deleted or untimed logs can be reconstructed.
- Run inside ordinary collector captures; no extra collector, polling, quota
  RPC, benchmark request, or report-triggered scan.
- Preserve the existing normal-tail capture limits and priority. Share a bounded
  historical-recovery budget with image backfill rather than independently
  adding another unbounded workload. Preserve image recovery fairness/progress.
- Reuse guarded source checkpoints and staged promotion. Bound bytes, open
  sources, and retained parser state; resume after interruption. Never commit a
  timing batch against a changed/unverified source generation.
- Missing logs and formats without usable timing get explicit terminal reasons;
  they must not remain perpetually pending or count as measurable coverage.
- New append timing is collected alongside normal parsing. Historical recovery
  reads/joins existing trusted usage; it must not duplicate language events.
  Retain already accepted historical timing when source logs subsequently
  disappear, consistently with durable language-event retention.
- Expose pending/measured/unmeasurable progress so partial charts are honest.

### Ledger-Only Views And Safe Interaction

- Add indexed speed queries and cache aggregates/rendered output by speed
  revision, metric version, date bounds, project keys, timezone, and chart window.
- Warm unchanged HTML does zero timing scans/reaggregation, historical decoding,
  source opens, capture, probes, or allowance repricing. Window navigation must
  not require reopening/revaluing the complete usage history.
- Preserve script-disabled webviews and CSP. Use semantic HTML/SVG/CSS and
  narrowly allowlisted host commands for stateful navigation. Validate command
  argument shapes/types/bounds; reject stale or out-of-range window requests.
- Advertise additive collector capability/status fields and keep older optional
  status fields compatible. A mismatched collector must fail visibly, not
  silently display fabricated or stale speed values.

## Observable Acceptance And Verification

- Timing tests cover reasoning counted once; all-field reconciliation; missing,
  collapsed, negative and overlapping intervals; late tool completions; aborted
  responses; duplicate/inherited/conflicting IDs; and every critical checkpoint
  boundary. Full and append parsing produce the same accepted facts.
- Schema-5 upgrade retains existing facts and leaves a readable private backup.
  Cache schema migration retains usage and checkpoints. Replacement/rekey,
  ownership normalization, missing files, restart, and interrupted recovery do
  not duplicate, orphan, or cross-bind timing observations.
- All available history progresses in bounded fair batches while normal new-tail
  and image capture continue. Repeating an unchanged capture is idempotent.
- On frozen disposable data, every existing token, USD, Standard-credit, image,
  allowance, and indexed/full monetary result matches the baseline exactly.
  Speed-only revisions do not trigger monetary recomputation.
- Median/IQR/sample counts match an independent fact-level oracle under range,
  subset, transition, and timezone filters, including both DST transitions.
  Sparse, empty and partially recovered charts show honest gaps/reasons.
- Measure initial migration/materialization, each backfill slice, append capture,
  quota-only update, warm HTML, and window/filter changes separately. Add work
  counter assertions for zero warm scans/fit/repricing and bounded slice work;
  record timing evidence without introducing flaky wall-clock CI thresholds.
- Extension tests cover true All Projects with future projects, explicit fixed
  subsets, duplicate labels, cancellation, timing-only refresh, retained chart
  state, and invalid/stale navigation arguments. Usage reload is absent while
  Storage reload and the recovery command remain available.
- Verify Day/Night and wide/narrow views (including 360 px), keyboard detail,
  labels, gaps, multi-model ranges, and navigation in Chromium/WebKit/Firefox.
  Exercise controls in the actual script-disabled VS Code webview with a
  disposable home/install, not just a permissive browser harness.
- Follow established gates: `uv run pytest -q`, `uv run ruff check .`, extension
  tests/build, screenshot checks, and macOS ARM64/Windows x64 package smoke,
  archive, and disposable handoff gates. Extend packaged smoke checks to timing
  migration/recovery. CI failures or missing material gates block publication.
- Review before release. Require exact-commit nonpublishing CI before the tag;
  verify both published Marketplace targets and public VSIX SHA-256 equality
  with the exact publication artifacts. Private corpus data stays unpublished.

## Permissions, Rollback, And Exclusions

- Implementation, scoped commit/push, and release are approved. Version/tag
  and Marketplace publication follow candidate acceptance and the established
  exact-commit platform gates; no PR is required.
- Verification uses synthetic homes and disposable ledger/log copies. Do not
  alter the user's live ledger, installed extension, Codex files, services,
  settings, or tunnel configuration to perform acceptance checks.
- An ordinary user upgrade may migrate its ledger and recover timing during
  normal capture, with the established backup contract. Test downgrade against
  a disposable pre-migration backup: an older collector may reject the new
  schema. Never silently restore an old backup over post-upgrade captures.
- Preserve prepared tracked reload edits and the unrelated untracked `apps/`.
- No standalone app, ChatGPT/private-MCP expansion, remote telemetry, network
  benchmarks, new pricing/capture frequency, task deletion/transfer changes,
  default effort splits, or automatic claim that the announced 50% gain has
  been verified. Workload mix, routing, client timing, and missing evidence
  remain material limits on interpreting the trends.
