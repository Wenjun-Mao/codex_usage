# Codex Usage 2.9.0: Extension-Only Distribution

## Goal

Retire the separate macOS and Windows native app. Keep the VS Code Companion's
current Usage, Task Storage, Task Transfer, capture, export, and report UI.
The extension remains self-contained on its supported platforms and continues
to bundle the Python collector. No ledger reset, recapture, or change to usage
accounting is part of this work.

The intended trade-off is explicit: scheduled capture runs while VS Code is
open, even with the dashboard closed, but stops when VS Code exits. Quota
snapshots missed during that interval cannot always be reconstructed later.
This fits the current primary use case, in which VS Code stays open.

## Decision And Boundaries

Retire the native product rather than merely freezing new preview builds. A
freeze would avoid an immediate migration but leave the second UI, Tauri/Rust
dependencies, fixtures, and support surface to maintain. Removing all service
compatibility immediately is also unsafe: existing users may still have a
native-installed background collector. Preserve a narrow, explicit retirement
path for that service; do not retain or introduce a new unattended daemon.

Keep the shared Python ledger, pricing, HTML report renderer, authenticated
collector API, and platform-specific VSIX binaries. Do not change Codex task
data, ledger identity, historical captures, release history, or unrelated
features. Historical ADRs and changelogs remain historical; a new ADR
supersedes the active distribution/lifecycle portions of ADRs 0034 and 0036
and names the extension/shared report styling as the continuing visual
authority from ADR 0037.

## Delivery Order

1. **Prove extension independence.** Map and test every VSIX build dependency
   on `apps/desktop`, especially PyInstaller output under
   `apps/desktop/src-tauri/binaries`. Move collector packaging to a neutral or
   extension-owned build location. Verify both packages still contain exactly
   one matching executable and no Tauri files or opposite-platform binary.
2. **Handle existing native background registrations.** Add an opt-in,
   Command-Palette-accessible handoff in VS Code. Detect only the known Codex
   Usage LaunchAgent/Windows Scheduled Task and active collector owner; explain
   that capture outside VS Code will stop. After confirmation, unregister that
   service without touching the ledger or Codex tasks, wait for its writer to
   exit, then acquire the bundled parent-bound collector. Verify the same
   `CODEX_HOME`, ledger revision/history, and successful subsequent capture.
   Leave an actionable recovery path if handoff fails. Do not silently stop a
   background collector during extension update or first activation. On this
   Mac the known LaunchAgent plist was absent at planning time; other users
   may still require the handoff.
3. **Remove the native client surface.** Remove the Tauri frontend/host,
   desktop-only fixtures and release helpers, unsigned preview jobs, and the
   VS Code **Open App** button/command. Retain the existing report appearance
   and extension workflows. Remove native-only settings controls and update
   copy that implies the app is available; tolerate legacy serialized settings
   while retaining only compatibility needed to retire service registration.
4. **Move visual evidence to the product being shipped.** Replace active
   README/Marketplace native screenshots with deterministic, privacy-safe
   captures of the VS Code webview and Task Storage surface. Move screenshot
   generation and allowance visual checks off the native fixture while keeping
   wide/narrow, Day/Night, interaction, accessibility, and clipping coverage.
   Do not present obsolete native screenshots as the current UI.
5. **Update release contract and documentation.** Make CI validate Python,
   Ruff, extension tests, packaged collector smoke checks, VSIX content, and
   the new visual gate on macOS ARM64 and Windows x64. Publication continues
   only after both platform VSIX jobs pass. Update setup, support, uninstall,
   and release docs; add the superseding ADR and 2.9.0 changelogs/version
   metadata. Tell existing users to uninstall the native preview only after
   service handoff, without deleting shared Codex Usage data. Remove native
   packaging requirements, not core ledger tests.

## Acceptance

- On macOS ARM64 and Windows x64, a clean VSIX install can choose `CODEX_HOME`,
  capture, render Usage/Plan Allowance/Task Storage, export, and perform Task
  Transfer without the native app or its files. The dashboard's existing
  controls and layout remain, except for **Open App**.
- With VS Code open and its dashboard closed, scheduled capture continues at
  the configured interval. Closing the final extension host stops only its
  parent-bound collector. Reopening resumes against the same ledger without
  duplicate writer or data loss. The report must not imply continuous quota
  coverage across a VS Code downtime gap when snapshots were missed.
- A legacy registered background service is never removed automatically.
  The explicit handoff preserves settings, event IDs, and ledger revision,
  eliminates the known OS registration, and yields exactly one VS Code-owned
  writer; refusal leaves the existing service undisturbed. Failure is visible
  and recoverable without **Reset Local Data**.
- Range/project/theme changes and exports remain ledger-only. Package and
  release tests no longer require Tauri, Cargo, DMG, or NSIS. Both VSIX
  variants pass local and non-publishing CI gates before a 2.9.0 tag/publish.
- Canonical screenshots depict the extension, contain no local corpus/private
  paths, and pass Day/Night wide/narrow visual and interaction checks.

## Risks And Open Implementation Choices

- The legacy service may point to a now-missing native binary. Detection and
  unregistration must work from the bundled collector without launching that
  binary, and must avoid touching unrelated OS services.
- The extension currently attaches to any healthy collector for the selected
  home. During transition, an older background owner may remain active until
  the user chooses handoff. Keep compatibility/error messaging clear; never
  claim extension ownership before it is verified.
- The implementer may choose the exact fixture/harness and command wording,
  provided the screenshots exercise production webview HTML/CSS and the
  migration is explicit, reversible where feasible, and tested on both OSes.
